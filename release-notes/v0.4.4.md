# xray-pilot v0.4.4

Two node-level configuration overrides: Reality SNI / fingerprint can now be overridden per node, and the log level can be tuned per node.

## Fixed

### Node-level SNI / fingerprint overrides now actually take effect

Until now the SNI and TLS fingerprint were read **only from the protocol template** in all four generation paths — subscription URI, Clash, sing-box and the xray inbound — because the node key material struct did not even carry those fields. Editing SNI in the node profile drawer therefore did nothing, and subscriptions kept the template value.

`RealityKeyMaterial` now has `sni` / `fingerprint` fields, and all four paths go through the `EffectiveRealitySNI` / `EffectiveRealityFingerprint` helpers with this precedence:

```
node key override  >  protocol template  >  default (www.microsoft.com / chrome)
```

To change the SNI for one node: open the node profile drawer → edit the `sni` field in the Reality key JSON and save (unlock a bound profile first) → press sync. The UI's one-click generate now also seeds the template's sni / fingerprint as an editable starting value.

### Node-level log level override

Log level used to be a single global switch, so turning on `debug` for one misbehaving node raised the log volume for all of them.

The node edit drawer now has an "Xray runtime settings · Log level" dropdown: leave it blank to inherit the system setting, or set `debug` / `info` / `warning` / `error` / `none` for that node only. It takes effect after a sync.

## Upgrade

- The `nodes` table gains a nullable `log_level` column (added automatically by GORM AutoMigrate; blank means inherit the global setting, so existing data is untouched)
- No breaking API changes
- Existing nodes only pick up node-level SNI if you open the drawer and fill in `sni`, then sync; otherwise behaviour is unchanged (inherit the template)

## Notes

- Both overrides need a sync to reach the node
- The node-level SNI override follows the project's existing per-node override convention: every consumer goes through the helper instead of reading the template directly (the same pattern as `effectiveKeyPort`)
