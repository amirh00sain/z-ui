# xray-pilot v0.4.3

Fixes a data bleed where a node created after deleting another inherited its groups, profiles and user links.

## Fixed

### Deleting a node now cascades through the relation tables

Deleting a node used to run only `DELETE FROM nodes`, leaving the matching rows in `group_nodes` (node–group) and `node_profile_keys` (node–profile key) behind. Combined with SQLite reusing the highest deleted ID on the next INSERT, a one-click provisioned node could land on an old node ID and "inherit" its groups, profiles and users.

Deleting a node is now a transaction across all three tables: `group_nodes` → `node_profile_keys` → `nodes`.

### One-time orphan cleanup at startup

The first start after upgrading to v0.4.3 runs an orphan sweep across six directions:
- `group_nodes` pointing at nodes or groups that no longer exist
- `node_profile_keys` pointing at nodes or profiles that no longer exist
- `user_groups` pointing at users or groups that no longer exist

Leftover dirty data from earlier versions is cleaned up in that pass. **Only orphan rows are touched — valid relations are left alone.**

## Upgrade

- No schema changes and no breaking API changes
- After starting, re-check any recently provisioned nodes in the node list to confirm their group, profile and owner fields are right (if anything is still wrong you can fix it by hand; the next startup sweep will clear the rest)

## Notes

- This release does not switch to soft deletes (GORM `DeletedAt`), so ID reuse can still happen. With the cascade and the startup sweep, however, a reused ID no longer bleeds data
- Soft deletes would be a wide change (every node query needs `WHERE deleted_at IS NULL`, unique constraints become partial indexes), so they are out of scope here
